# 1.3. Variant calling

The goal of variant calling is to determine, at every position of the reference, the alleles carried by our sample individuals - or their **genotypes**. Unfortunately, we never observe the genotypes directly. Instead, we are forced to work with piles of aligned (short) reads: these might be misplaced, carry errors, or be too scarce to provide sufficient information for a confident genotype call. Calling is therefore a statistical endevour.

## (1.3.1) Calling prep

We will use `bcftools` to perform variant calling. The software uses a **joint calling** strategy, originally designed to accommodate for low-coverage samples ([Li, 2011](../papers/li2011.pdf)): a weakly supported non-reference allele in sample A gains credibility if it's also found in sample B. While many more modern variant callers exist (see box below), `bcftools` has stood the test of time ([Danacek, 2021](../papers/danecek2021.pdf); [Lefouili and Nam, 2022](../papers/lefouili2022.pdf)) and can be seamlessly integrated with `samtools` to demonstrate calling principles.

!!! tip "Variant calling algorithms"
    Apart from `bcftools`, several other calling algorithms, varying in their calling principles, are in common use. **GATK `HaplotypeCaller`**, for example, performs local haplotype assembly to identify variant sites (more on that in the bonus section 1.3.7) and is likely the most widely used caller in human genomics. **`freebayes`** takes a similar haplotype-based approach but with a simpler Bayesian model. Finally, **DeepVariant** replaces the statistical model entirely: it turns the alignment into an image-like representation and classifies genotypes with a neural network trained on 'truth sets'. Unfortunately, benchmark rankings for all of these are built almost entirely on human datsets ([Kumaran et al., 2019](../papers/kumaran2019.pdf)).

As a reminder, you should still be in your private `reads2snps` directory. The first task in this worksheet is to prepare a list of BAM files for joint calling. We will use the `sed` stream editor to write their **paths** to a text file based on the stored sample names.

```bash
# Just a reminder!
cd ~/reads2snps

# Define input & output names
SAMPLES=./samples.txt
BAMS=./bams.txt

sed 's|.*|2.aligned/&.bam|' $SAMPLES > $BAMS
cat $BAMS
```

In the `sed` command, `s|old|new|` allows us to **substitute** whatever matches the first part with the second. The pattern `.*` is a regular expression that matches any character (`.`) repeated any number of times (`*`). The matched characters are then substitued instead as `&` inside the longer `2.aligned/&.bam` strings. Neat, isn't it?

!!! tip "Glob alternative"
    Alternatively, the BAM-path file could be written with `printf '%s\n' 2.aligned/*.bam > "$BAMS"`. Then, however, you'd need to be sure that you want to include all the BAMs in the `2.aligned` directory. Today, the answer is likely 'yes', but it is generally good practice to explicitly define the inputs based on a config. 
    

## (1.3.2) Variant calling with `bcftools`

Variant calling with `bcftools` consists of two steps: **(1)** `mpileup`, that, for each vertical 'slice' through the given alignment (i.e., site), computes genotype likelihoods (based on base qualities, read mapping qualities, etc.) and **(2)** `call`, that evaluates the most likely genotypes under the assumption of Hardy-Weinberg equilibrium ([Danacek, 2021](../papers/danecek2021.pdf)). The two commands can be piped together so the intermediate never touches disk, and the final output is recorded as a **VCF (variant call format) file**. Run the caller, and then we'll break things down.

```bash
# BCFtools mpileup / call inputs
REF=./ref/chrom1_1Mb.fa
BAMS=./bams.txt

# BCFtools mpileup / call output
VCF_PREFIX=./3.calls/bcftools/littorina

# Commands
mkdir -p ./3.calls/bcftools
bcftools mpileup \
    -a FORMAT/AD,FORMAT/DP,FORMAT/SP,INFO/AD \
    -f $REF \
    -b $BAMS \
    -Ou |
bcftools call \
    -m \
    -f GQ,GP \
    -Oz \
    -o ${VCF_PREFIX}.vcf.gz
```

Note that we used a VCF_PREFIX rather than a VCF variable - this will make it easier to create multiple VCF files differing by suffixes, and there'll be a couple in the next worksheet. Now, what do the different flags mean?

`bcftools mpileup`:

- `-a` annotates each site record with extra fields that are not emitted by default. You will be able to better understand what these mean once we've inspected a VCF file (see below) and performed some filtering (next worksheet), so be sure to revisit this command later.
- `-f` and `-b` specify the reference FASTA and BAM-list file, respectively.
- `-Ou` specifies that the output (`-O`) should be in an *uncompressed BCF* format (`u`). The BCF format is a binary VCF counterpart, and using it in a pipe is the most efficient option. 

`bcftools call`:

- `-m` ensures that multiallelic sites are correctly called.
- `-f GQ,GP` IN ADDITION TO CALLING VARIANTS, WE WANT TO ADD(again, revisit later) adds two per-sample quality fields to the VCF file: `GQ`, the Phred-scaled confidence in the genotype that was called, and `GP`, the posterior probability of each possible genotype. `GQ` is what the soft filters in the next worksheet use to mask individual genotypes they do not believe. 
- `-Oz` specifies a *compressed VCF* output - hence the `.vcf.gz` extension.

One commonly included option that we deliberately **avoided** is `-v` (or `--variants-only`) used with `bcftools call`. Passing `-v` would emit only variant sites, dropping all sites where no alternative alleles were called. This, however, makes it more difficult to compute nucleotide diversity ($\pi$) and divergence ($d_{xy}$) that are per-base quantities.

!!! tip "On VCF compression"
    Note that VCF files produced with `-Oz` are compressed using [`bgzip`](https://www.htslib.org/doc/bgzip.html) and not plain `gzip`. This is important to keep in mind if you ever want to compress a VCF manually. 

## (1.3.3) The VCF format

A full desciption of the VCF format can be found [here](https://samtools.github.io/hts-specs/VCFv4.2.pdf), but we will now walk through its most important aspects.

A VCF consists of two main components - the header and the 'body' (consiting of site records). Let's examine the header first.

```bash
bcftools head ${VCF_PREFIX}.vcf.gz | less -S

# Or the below
# bcftools view -h ${VCF_PREFIX}.vcf.gz | less -S
```

Note that all but the final displayed line start with `##`. The first line always states the VCF format version, here `VCFv4.2`. You should also find lines descibing the `bcftools` version and commands used. One striking pattern in the header are the repeated `##INFO` and `##FORMAT` lines. We can examine one as below.

```bash
zcat ${VCF_PREFIX}.vcf.gz | grep "##INFO" | tail -1
##INFO=<ID=MQ,Number=1,Type=Integer,Description="Average mapping quality">
```

You will notice that this is essentially a dictionary, where `MQ` is represented once (`Number=1`), is of type `Integer` and described as `Average mapping quality`. These dictionaries describe the data stored in our VCF. In fact, the final line of the header (which starts with a single `#`) contains data column names, one of them being `INFO` - perhaps that's where we should expect to find the `MQ` field! Let's turn to examining the data lines.

```bash
bcftools view ${VCF_PREFIX}.vcf.gz | grep -v '^##' | less -S

# Or the below, without column names
# bcftools view -H ${VCF_PREFIX}.vcf.gz | less -S
```

You can now see the data columns with their corresponding names - however, since the fields are tab-separated and vary a lot in width (and there can be many sample columns), the names rarely line up neatly above their values on screen, so you will need to count columns and names to match them up. Each data line corresponds to a site in the reference sequence and is described by the following columns:

- **CHROM** — the name of the reference sequence (chromosome or contig) the site sits on. This matches a `##contig` line in the header and the name in your reference genome (e.g. `NC_090245.1`).
- **POS** — the 1-based position of the site on that chromosome. For indels this is the leftmost affected reference position.
- **ID** — a variant identifier (for example a dbSNP `rs` number) if one exists, otherwise `.`. Freshly called variants are usually `.`.
- **REF** — the reference allele: the base(s) present at this position in the reference genome.
- **ALT** — the alternate allele(s) actually observed in the data, comma-separated if there is more than one (e.g. `A,T`). A `.` means no alternate was found — i.e. a non-variant (invariant) site.
- **QUAL** — a Phred-scaled quality score for the assertion that an ALT allele is present: higher means more confident (30 ≈ 99.9% confident). It is `.` when not calculated.
- **FILTER** — `PASS` if the site passed every filter, otherwise a semicolon-separated list of the filters it failed (each defined in a `##FILTER` header line). A `.` means no filtering has been applied yet.
- **INFO** — site-level annotations as a semicolon-separated list of `key=value` pairs (e.g. `MQ=60;DP=45`), where every key is defined by a `##INFO` line. This is where our `MQ` field lives — exactly as we predicted from the header.
- **FORMAT** — a colon-separated list of keys defining the per-sample fields that follow, and the order they appear in (e.g. `GT:DP:GQ:PL`). Each key is defined by a `##FORMAT` line.
- **Sample columns** — one column per sample, each holding colon-separated values that line up, in order, with the `FORMAT` keys (e.g. `0/1:45:99:255,0,255`). The first sub-field is almost always **GT**, the genotype, encoded against the REF/ALT alleles: `0` = REF, `1` = first ALT, `2` = second ALT, and so on. So `0/0` is homozygous reference, `0/1` heterozygous, `1/1` homozygous alternate, and `./.` a missing genotype.

## (1.3.4) Extracting info

Reading a VCF with `less` is fine for exploration, but the format is not something you want to parse by hand. Luckily, all the useful information can be pulled out of a VCF using `bcftools query`. For example, the sample names:

```bash
bcftools query -l ${VCF_PREFIX}.vcf.gz | head
```

Or defined fields:

```bash
bcftools query -i 'TYPE="snp"' -f '%CHROM\t%POS\t%REF\t%ALT\t%QUAL\t%INFO/DP[\t%GT:%DP]\n' ${VCF_PREFIX}.vcf.gz | head
```

In the above command, note the following:

- `-i 'TYPE="snp"'` keeps only SNP records - assuming we are only interested in those.
- `%` marks a field; everything else is printed to output literally (`\t` is a tab and `\n` is a new line character).
- `INFO/` before `DP` is required to dinstinguish between site-level and sample-level values.
- Square brackets loop over sample-level values in `bcftools query -l` order. Note the positioning of `\t`....

Now the interesting question - how many different sites are present in our VCF?

```bash
bcftools stats

# If you want a clean...
bcftools stats ${VCF_PREFIX}.vcf.gz | grep "^SN" | cut -f3,4
```

## (1.3.5) VCF indexing

Sometimes you might only want to access only a section of your VCF. While we won't be doing that later on, just for the record:

```bash
bcftools index ${VCF_PREFIX}.vcf.gz
```

This produces a `.csi` index file, and this is what makes accessing different regions of your reference possible:

```bash
bcftools view -H -r NC_090245.1:1-1000 ${VCF_PREFIX}.vcf.gz | wc -l
```

## (1.3.6) BONUS: an alternative calling strategy with `GATK`

You may realise that the addition of new samples would necessitate rerunning both the `bcftools mpileup` and `call` commands. While with our sample and file sizes this does not seem daunting, adding an additional sample to a realistic dataset
(say, 30 full-size *Littorina* genomes) means redoing the whole run - and many more hours of compute time. So - not trivial!

This issue is addressed by a calling strategy adopted by [**GATK (Genome Analysis ToolKit)**](https://gatk.broadinstitute.org/hc/en-us). GATK also splits calling into two steps: however, genotype likelihoods are first computed *independently* for each sample, with joint calling as the second step. While the first step is not obviously cheaper, it only ever has to be done **once per sample**. In other words, adding sample no 31 means that 30 / 31 samples have already been processed. 

(diagram)

Another potential advantage of GATK list in its approach to identifying variant positions itself. In contrast to scanning a pre-computed alignment, the per-sample `HaplotypeCaller` of GATK performs local re-assembly of candidate (or ['active'](LINK)) regions and realigns reads against the re-assembled haplotypes. This strategy has been shown to be particularly effective for the discovery of indels, many of which are missed by pileup-style callers (REF).

!!! tip "GATK"
    GATK is extensively documented, with [tutorials](https://gatk.broadinstitute.org/hc/en-us/sections/360007226631-Tutorials) and a [user forum](https://gatk.broadinstitute.org/hc/en-us/community/topics). Note that older GATK versions also included another calling algorithm, `UnifiedGenotyper`, which is essentially a pileup-style caller and of significantly less interest than `HaplotypeCaller`.

```bash
## Inputs:
# We need a list of gVCFs
ls $GVCF_DIR/*.g.vcf.gz | grep -v "littorina" | sort > gvcf.list

### Outputs:
GVCF_TMP=./3.calls/gatk/littorina.TMP.g.vcf.gz
VCF_FINAL=./3.calls/gatk/littorina.gatk.vcf.gz

## Commands:
# First, combine into a temporary gVCF...
gatk CombineGVCFs \
   -R $REF \
   --variant gvcf.list \
   -O $GVCF_TMP

# Then, actually perform joint calling! 
# GenotypeGVCFs needs a directory for writing intermediate files;
# on a typical comupter cluster, this would be /home/scratch or similar.
mkdir ./tmp
time gatk GenotypeGVCFs \
    --java-options "-Xmx4000m" \
    -R $REF \
    --heterozygosity 0.005 \
    --include-non-variant-sites \
    -V $GVCF_TMP \
    -O $GVCF_FINAL \
    --tmp-dir ./tmp
rm ${GVCF_TMP}*
rm -r ./tmp
```
Where the `--heterozygosity` value feeds into computing the prior probability that a locus is non-reference (across all samples). Following a [state-of-the-art variant calling pipeline](https://snparcher.github.io/) tailored to non-model organisms, we set a value that is five-fold higher than the default of 0.001 calibrated for human populations. You can read more on the `--heterozygosity` flag [here](https://gatk.broadinstitute.org/hc/en-us/articles/360035890871-Heterozygosity).

!!! tip "More on GATK"
