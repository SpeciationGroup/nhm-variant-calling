# 1.3. Variant calling

!!! abstract "Learning objectives"
    By the end of this worksheet, you will:

    - Call variants with BCFtools.
    - Understand the structure of a VCF file.
    - Interrogate VCFs with BCFtools.
    - BONUS: call variants with GATK, if there is time.

The goal of variant calling is to determine, at every position of the reference, the alleles carried by our sample individuals - or their **genotypes**. Unfortunately, we never observe the genotypes directly. Instead, we are forced to work with piles of aligned (short) reads: these might be misplaced, carry errors, or be too scarce to provide sufficient information for a confident genotype call. Calling is therefore a statistical endeavour.

## (1.3.1) Calling prep

We will use BCFtools to perform variant calling. The software uses a **joint calling** strategy, originally designed to accommodate for low-coverage samples ([Li, 2011](../papers/li2011.pdf)): a weakly supported non-reference allele in sample A gains credibility if it's also found in sample B. While many more modern variant callers exist (see box below), BCFtools has stood the test of time ([Danacek, 2021](../papers/danecek2021.pdf); [Lefouili and Nam, 2022](../papers/lefouili2022.pdf)) and can be seamlessly integrated with SAMtools to demonstrate calling principles.

!!! tip "Variant calling algorithms"
    Apart from BCFtools, several other calling algorithms, varying in their calling principles, are in common use. **GATK `HaplotypeCaller`**, for example, performs local haplotype assembly to identify variant sites (more on that in the bonus section 1.3.7) and is likely the most widely used caller in human genomics. **`freebayes`** takes a similar haplotype-based approach but with a simpler Bayesian model. Finally, **DeepVariant** replaces the statistical model entirely: it turns the alignment into an image-like representation and classifies genotypes with a neural network trained on 'truth sets'. Unfortunately, benchmark rankings for all of these are built almost entirely on human datsets ([Kumaran et al., 2019](../papers/kumaran2019.pdf)).

As a reminder, you should still be in your private `reads2snps` directory. The first task in this worksheet is to prepare a list of BAM files for joint calling. We will use the `sed` stream editor to write their **paths** to a text file based on the stored sample names.

```bash
# Just a reminder!
cd ~/reads2snps

# Define input & output names
SAMPLES=./samples.txt
BAMS=./bams.txt

sed 's|.*|2.aligned/&.bam|' $SAMPLES > $BAMS
cat $BAMS
```

In the `sed` command, `s|old|new|` allows us to **substitute** whatever matches the first part with the second. The pattern `.*` is a regular expression that matches any character (`.`) repeated any number of times (`*`). The matched characters are then substituted instead as `&` inside the longer `2.aligned/&.bam` strings. Neat, isn't it?

!!! tip "Glob alternative"
    Alternatively, the BAM-path file could be written with `printf '%s\n' 2.aligned/*.bam > "$BAMS"`. Then, however, you'd need to be sure that you want to include all the BAMs in the `2.aligned` directory. Today, the answer is likely 'yes', but it is generally good practice to explicitly define the inputs based on a config. 
    

## (1.3.2) Variant calling with BCFtools

Variant calling with BCFtools consists of two steps: **(1)** `mpileup`, that, for each vertical 'slice' through the given alignment (i.e., site), computes genotype likelihoods (based on base qualities, read mapping qualities, etc.) and **(2)** `call`, that evaluates the most likely genotypes under the assumption of Hardy-Weinberg equilibrium ([Danacek, 2021](../papers/danecek2021.pdf)). The two commands can be piped together so the intermediate never touches disk, and the final output is recorded as a VCF file. Run the caller, and then we'll break the commands down.

```bash
# BCFtools mpileup / call inputs
REF=./ref/chrom1_1Mb.fa
BAMS=./bams.txt

# BCFtools mpileup / call output
VCF_PREFIX=./3.calls/bcftools/littorina

# Commands
mkdir -p ./3.calls/bcftools
bcftools mpileup \
    -a FORMAT/SP,FORMAT/DP \
    -f $REF \
    -b $BAMS \
    -Ou |
bcftools call \
    -m \
    -a FORMAT/GQ \
    -Oz \
    -o ${VCF_PREFIX}.vcf.gz
```

Note that we used a VCF_PREFIX variable **without an extension**. This will make it easier to create multiple VCF files with different extensions, and we'll see a couple in the next worksheet. Now, what do the different flags mean?

`bcftools mpileup`:

- `-a` annotates each record with extra fields (`FORMAT/SP`and `FORMAT/DP`) that are not emitted by default. Exactly what these mean will become clear once we inspect the VCF file (see below).
- `-f` and `-b` specify the reference FASTA and BAM-list file, respectively.
- `-Ou` specifies that the output (`-O`) should be in an uncompressed BCF format (`u`). The BCF format is a binary counterpart of VCF (think of SAM -> BAM); here, it's just used inside the pipe for efficiency.

`bcftools call`:

- `-m` selects the 'multiallelic caller' algorithm instead of an older 'consensus caller' (`-c`), which can detect at most one alternative allele per site. Neither of these options is default, and one of them needs to provided.
- `-a` is analogous to `mpileup -a` but adds fields specific to the `call` stage. Think of the division of labour between the two commands - while `mpileup` handles reads, `call` works with genotypes. Some annotations are derived from directly from the latter (more on that later).
- `-Oz` specifies a compressed VCF output, hence the `.vcf.gz` extension.

One commonly included option that we deliberately **avoided** is `-v` (or `--variants-only`) used with `bcftools call`. Passing `-v` would emit only variant sites, discarding all invariant sites, where no alternative alleles have been called. This interferes with calculating population genetic statistics such as nucleotide diversity ($\pi$) and divergence ($d_{xy}$), so we recommend you avoid this flag, if possible.  

!!! tip "On VCF compression"
    Note that VCF files produced with `-Oz` are compressed using [`bgzip`](https://www.htslib.org/doc/bgzip.html) and not plain `gzip`. Keep this in mind, since bgzip-compression is required by some commands such as `bcftools index`.
    
## (1.3.3) The VCF format

The VCF (Variant Call Format) is defined in full [here](https://samtools.github.io/hts-specs/VCFv4.2.pdf); today we'll just cover its most important aspects.

Similarly to a SAM, a VCF splits into a header and a 'body'. Since it's a tradition by now, let's examine the header first. BCFtools is used not only for calling but for manipulating VCFs generally, and it has a dedicated command for this:

```bash
bcftools head ${VCF_PREFIX}.vcf.gz | less -S
```

Note that all but the final displayed line start with `##`. The first always states the VCF format version - here `VCFv4.2` - and further down you should find the BCFtools version and the commands that produced the file. Most of the header, though, is taken up by repeated `##INFO` and `##FORMAT` lines. Let's examine one:

```bash
zcat ${VCF_PREFIX}.vcf.gz | grep "##INFO" | tail -1
```

Where `tail -1` extracts the final line of the input. Notice how the `##INFO` line is essentially a dictionary entry: the key `MQ` takes an `Integer`, and it means `Average mapping quality`. 

Now, can you recall the `-a` flag we passed to `mpileup` and `call`? The codes we asked for there - `FORMAT/SP`, `FORMAT/SP`, `FORMAT/GQ` - carry the same two prefixes as encountered in the VCF header, and for good reason. `INFO` and `FORMAT` are **columns of the VCF body**, each gathering a set of annotations that the header defines one by one. Every annotation therefore appears in two places - declared once in the header, and then carried as a value by those records it applies to. Let's turn to the data lines to see them. We will use another useful BCFtool command:

```bash
# grep -v matches lines that DON'T contain a pattern
bcftools view ${VCF_PREFIX}.vcf.gz | grep -v '^##' | less -S

# Or the below, without column names
# bcftools view -H ${VCF_PREFIX}.vcf.gz | less -S
```

You can now see the data columns with their corresponding names (top line). Unfortunately, since the columns are tab-separated and vary a lot in width, the names rarely line up neatly above their values on screen. Below column names, each line corresponds to a **record** - a variant or an invariant site. 

Here is a breakdown of the columns that define the records:

- **CHROM** — the name of the reference sequence the site sits on. This matches a `##contig` line in the header.
- **POS** — position of the site along the reference. For indels this is the last unaffected base immediately preceding the event.
- **ID** — a variant identifier. Freshly called variants are usually `.`.
- **REF** — the reference allele: the base(s) present at this position in the reference genome.
- **ALT** — the alternate allele(s) called in the data, comma-separated if there is more than one (e.g. `A,T`). A `.` means no alternate was found (invariant site).
- **QUAL** — a Phred-scaled quality score for the assertion made in the ALT column. Both variant and invariant sites can carry a QUAL value, though it is occasionally `.`.
- **FILTER** — `PASS` if the site passed every filter, or a semicolon-separated list of the filters it failed (each defined by a `##FILTER` line). A `.` means no filtering has been applied yet - as is the case for our freshly called VCF.
- **INFO** — annotations defined at **site-level**, given as a semicolon-separated list of `key=value` pairs (e.g. `DP=65;MQ=15`, etc.). Each key is defined by an `##INFO` line. A given score describes the record as a whole.
- **FORMAT** — annotations defined at **sample-level**, given as a colon-separated list of **keys only**. Each key is defined by a `##FORMAT` line. The order of FORMAT annotations is replicated in the sample fields (see below).
- **Sample columns** — one column per sample, each holding a colon-separated list consisting of a **genotype** and values defined by the FORMAT column. The genotypes are encoded against the REF/ALT alleles: `0` = REF, `1` = first ALT, `2` = second ALT, and so on. Accordingly, `0/0` is homozygous reference, `0/1` heterozygous, `1/1` homozygous alternate, whereas `./.` is a missing genotype.

Some of the above definitions might sound somewhat abstract. The key thing to understand is **the relationship between the INFO, FORMAT and sample columns**, so do spend time trying to relate them to one another.

## (1.3.4) Interrogating VCFs

Reading a VCF with `less` is fine for exploration - for extracting specific information, specialised BCFtools commands come to the rescue. Sample names, for example, can be extracted using `bcftools query` with the `-l` flag:

```bash
bcftools query -l ${VCF_PREFIX}.vcf.gz
```

A more elaborate `query` command extracts specific INFO and FORMAT annotations:

```bash
bcftools query -i 'TYPE="snp"' -f '%CHROM\t%POS\t%REF\t%ALT\t%QUAL\t%INFO/DP[\t%GT:%DP]\n' ${VCF_PREFIX}.vcf.gz | head
```

This prints a tab-separated table, ready for further analyses in R, for example. In the above command, note the following:

- **`-i 'TYPE="snp"'`** keeps only SNP records - assuming we are only interested in those.
- **`-f`** reads a string that requests specific fields:
    - `%` marks a field. Everything else is printed to output literally: `\t` is a tab and `\n` is a new line character.
    - `INFO/` before `DP` is required to distinguish between site-level and sample-level values; `DP` is represented in both INFO and FORMAT.
    - Square brackets loop over sample-level values (same order as `bcftools query -l`). Note the positioning of `\t` - it sits inside the brackets, so a tab is printed once per sample rather than once per line.

Just like SAMtools, BCFtools can print a summary report of the whole file. This will answer one fundamental question - how many, and what kind of, sites are present in our VCF?

```bash
bcftools stats ${VCF_PREFIX}.vcf.gz | less -S
```

Alright, that's another big report, and we're not saving this one to disk. Instead, using some of the tricks we learnt before - but now in combination with a `cut` command that extracts columns 3 and 4 - we can pull out just the summary numbers:

```bash
bcftools stats ${VCF_PREFIX}.vcf.gz | grep "^SN" | cut -f3,4
```

Now, we have a compact report: the number of records in the file, how many of them are 'no-ALTs' (= invariant sites), and a breakdown of the rest into SNPs, indels and multiallelic sites. Of course, we can request information in an even more streamlined manner. For example, just the SNP count:  

```bash
bcftools view -Hv snps ${VCF_PREFIX}.vcf.gz | wc -l
```

Where `-H` narrows down the output to just the VCF body, `-v snps` requests SNPs only, and `wc -l` counts lines. The number shoud be identical to that reported by `bcftools stats`!

Finally, especially with a big VCF, you could be interested in just interrogating a specific region of a specific chromosome. First, we need to index our VCF...

```bash
bcftools index ${VCF_PREFIX}.vcf.gz
```

...and only access our region of interest with `bcftools view`. This is specified with a string provided to the `-r` flag: 

```bash
bcftools view -H -r NC_090245.1:1-10 ${VCF_PREFIX}.vcf.gz | less -S
```

Where `NC_090245.1` is the name of our reference and `1-10` is the target range.

The moral is - bioinformaticians who work with VCF files typically use BCFtools every day, so familiarity with the different usage patterns is very useful (that's why we are spending time on it!). The [docs](https://www.htslib.org/doc/bcftools.html) are definitely your friend on this adventure.

## (1.3.6) BONUS: An alternative variant calling strategy with `GATK`

You may realise that the addition of new samples would necessitate rerunning both the `bcftools mpileup` and `call` commands. While this might not seem daunting with our sample and file sizes, adding an additional sample to a realistic dataset
(say, 30 full-size *Littorina* genomes) means redoing the whole run. So - not a trivial cost!

This issue is addressed by a calling strategy adopted by [**GATK (Genome Analysis ToolKit)**](https://gatk.broadinstitute.org/hc/en-us). GATK also splits calling into two steps: however, genotype likelihoods are first computed *independently* for each sample, with joint calling as the second step. While the first step is not obviously cheaper, it only ever has to be done **once per sample**. In other words, adding sample no 31 means that 30 / 31 samples have already been processed. 

Another potential advantage of GATK lies in its approach to identifying variant positions in the first place. Rather than scanning a pre-computed alignment, the per-sample `HaplotypeCaller` performs local re-assembly of candidate (or ['active'](LINK)) regions and realigns reads against the re-assembled haplotypes. This strategy has been shown to be particularly effective for the discovery of indels, many of which are missed by pileup-style callers (Poplin et al., 2017).

!!! tip "GATK"
    GATK is extensively documented, with [tutorials](https://gatk.broadinstitute.org/hc/en-us/sections/360007226631-Tutorials) and a [user forum](https://gatk.broadinstitute.org/hc/en-us/community/topics). Note that older GATK versions also included another calling algorithm, `UnifiedGenotyper`, which is essentially a pileup-style caller and of significantly less interest than `HaplotypeCaller`. 

We have pre-computed all the gVCFs, which you can find under `/home/Share/reads2snps/3.calls/gatk`. For practice, run the algorithm on one sample using the commands below.

First, GATK needs one additional indexing of the reference and the BAM:

```bash
REF=./ref/chrom1_1Mb.fa
samtools dict $REF -o ${REF%.fa}.dict

# Check what % does
echo ${REF%.fa}

SAMPLE=ACF_2
BAM=./2.aligned/${SAMPLE}.bam
samtools index $BAM
```

Run `HaplotypeCaller` for one sample:

```bash
# HaplotypeCaller inputs
SAMPLE=ACF_2
BAM=./2.aligned/${SAMPLE}.bam

# HaplotypeCaller outputs
GVCF_DIR=./3.calls/gatk

# Commands
mkdir -p $GVCF_DIR
gatk HaplotypeCaller \
    --java-options "-Xmx4000m" \
    -R $REF \
    -I $BAM \
    -O ${GVCF_DIR}/${SAMPLE}.g.vcf.gz \
    -ploidy 2 \
    --native-pair-hmm-threads 1 \
    --emit-ref-confidence GVCF
```

Where:

- **`--native-pair-hmm-threads`** sets the number of threads used by the read-to-haplotype alignment algorithm
- **`--emit-ref-confidence`** determines how likelihoods are emitted for non-variant sites. `GVCF` makes it score *every* position, but collapse runs of consecutive sites with comparable confidence into single 'reference blocks''.

??? success "The full `HaplotypeCaller` loop - just for reference"
    ```bash
    #!/bin/bash
    set -euo pipefail

    # Samples are read from a file, one name per line.
    IN_FILE=$1
    readarray -t SAMPLES < "$IN_FILE"

    # The reference and its dictionary are the same for every sample.
    REF=./ref/chrom1_1Mb.fa
    samtools dict $REF -o ${REF%.fa}.dict

    GVCF_DIR=./3.calls/gatk
    mkdir -p $GVCF_DIR $GVCF_DIR/logs

    for SAMPLE in ${SAMPLES[@]}; do
        echo "Starting sample ${SAMPLE}..."

        BAM=./2.aligned/${SAMPLE}.bam
        GVCF=${GVCF_DIR}/${SAMPLE}.g.vcf.gz
        LOG=${GVCF_DIR}/logs/${SAMPLE}.log

        samtools index $BAM

        # The & at the end sends this into the background, so the loop
        # starts the next sample instead of waiting. Each caller writes to
        # its own log - otherwise the messages of all samples would interleave.
        (
            gatk HaplotypeCaller \
                --java-options "-Xmx4000m" \
                -R $REF \
                -I $BAM \
                -O $GVCF \
                -ploidy 2 \
                --native-pair-hmm-threads 1 \
                --emit-ref-confidence GVCF \
                > $LOG 2>&1
            echo "Finished sample ${SAMPLE}."
        ) &
    done

    # Without this, the script would exit while the callers are still running.
    wait
    echo "All samples done."
    ```

!!! tip "GATK"
    Examine the gVCF yourself and try spotting the differences from a regular VCF!

Oof, `HaplotypeCaller` did not run instantaneously - as expected - but remember this is done only once per sample. Let's copy over all the pre-computed gVCFs...

```bash
GVCF_DIR=./3.calls/gatk
# This copies both .g.vcf.gz and .g.vcf.gz.tbi index files
cp /home/Share/reads2snps/3.calls/gatk/*.g.vcf.gz* $GVCF_DIR
```

...and combine them into one:

```bash
# CombineGVCFs inputs
# Rather than 11 arguments, we pass a file listing the gVCFs.
# The grep excludes our own output, in case you run this twice.
GVCF_DIR=./3.calls/gatk
ls $GVCF_DIR/*.g.vcf.gz | grep -v "/littorina" | sort > gvcf.list

# CombineGVCFs outputs
REF=./ref/chrom1_1Mb.fa
GVCF_TMP=./3.calls/gatk/littorina.TMP.g.vcf.gz

# Commands
gatk CombineGVCFs \
   -R $REF \
   --variant gvcf.list \
   -O $GVCF_TMP
```

Finally, we are ready to perform joint calling:

```bash
# GenotypeGVCFs outputs
VCF_FINAL=./3.calls/gatk/littorina.gatk.vcf.gz

# Commands
# GenotypeGVCFs needs a directory for writing intermediate files;
# on a typical computer cluster, this would be /home/scratch or similar.
mkdir ./tmp
time gatk GenotypeGVCFs \
    --java-options "-Xmx4000m" \
    -R $REF \
    --heterozygosity 0.005 \
    --include-non-variant-sites \
    -V $GVCF_TMP \
    -O $VCF_FINAL \
    --tmp-dir ./tmp

# The combined gVCF and the temporary directory are no longer needed
rm ${GVCF_TMP}*
rm -r ./tmp
```
Where the `--heterozygosity` value feeds into computing the prior probability that a locus is non-reference (across all samples). Following a [state-of-the-art variant calling pipeline](https://snparcher.github.io/) tailored to non-model organisms, we set a value that is five-fold higher than the default of 0.001 calibrated for human populations. You can read more on the `--heterozygosity` flag [here](https://gatk.broadinstitute.org/hc/en-us/articles/360035890871-Heterozygosity).

!!! tip "More on GATK"
    In a real pipeline, you'd probably prefer `GenomicsDBImport` over `CombineGVCFs` (see [GATK best practices](https://gatk.broadinstitute.org/hc/en-us/sections/360007226651-Best-Practices-Workflows)). The former produces a 'GenomicsDB workspace' rather than a single combined gVCF, which scales far better as samples accumulate.
