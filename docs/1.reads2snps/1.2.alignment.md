# 1.2. Alignment to reference

!!! abstract "Learning objectives"
    By the end of this worksheet, you will:

    - Map reads with BWA and process the output with SAMtools.
    - Understand the structure of a SAM / BAM file.
    - Perform some basic QC on a SAM / BAM.

In this tutorial we will use the BWA-MEM algorithm from the [BWA](https://github.com/lh3/bwa) (Burrows-Wheeler Aligner) package is the most widely used short read aligner. BWA uses the [Burrows-Wheeler Transform](https://www.youtube.com/watch?v=0qMGAsrYS0g) to reorganise the reference genome into an index in which any sequence can be looked up directly, rather than compared against the genome position by position. Today, we will be using [BWA-MEM2](https://github.com/bwa-mem2/bwa-mem2), a faster incarnation of the original algorithm that produces identical alignments; even [faster algorithms](https://github.com/lh3/minibwa) are on the horizon, so keep an eye for the future.

## (1.2.1) The reference

We do need a reference genome assembly for aligning our reads. We will download it from a public archive hosted by [NCBI](https://www.ncbi.nlm.nih.gov/). As always, it's reasonable to create a new directory to store the reference:

```bash
mkdir ./ref
```

We're going to use the US_GU_Lsax_2.0 assembly - search for *Littorina saxatilis* in the [NCBI genome browser](https://www.ncbi.nlm.nih.gov/datasets/genome/) or, alternatively, open [this link](https://www.ncbi.nlm.nih.gov/datasets/genome/GCF_037325665.1/) directly. Try locating the 'FTP' button. FTP stands for File Transfer Protocol and is a convention for serving files over a network - here, it simply takes you to a plain directory listing of everything NCBI holds for this assembly. Copy the link to the file ending in `_genomic.fna.gz` (alternatively, we pasted it below!).

We can now download the assembly using the `wget` command, specifying `./ref` as the target directory:

```bash
wget https://ftp.ncbi.nlm.nih.gov/genomes/all/GCF/037/325/665/GCF_037325665.1_US_GU_Lsax_2.0/GCF_037325665.1_US_GU_Lsax_2.0_genomic.fna.gz \
--directory-prefix=./ref
```

!!! tip "FASTA extensions"
    Note that `.fa`, `.fasta` and `.fna` are all acceptable extensions for FASTA files - the latter just specifies that we're dealing with nucleic acids.

As always, let's inspect the FASTA's statistics with `seqkit stats`:

```bash
# -N 50 appends N50 as an extra column
seqkit stats -N 50 ./ref/*
```

That's a decent-sized metazoan genome!! It's approximately 12 times larger than the *C. elegans* genome, for example, but still 2.5 times smaller than the human genome. As indicated by the N50 statistic, it's also well-assembled, with half of the assembly in pieces longer than 67.5 Mb. This is chromosome-scale.

Aligning a decent depth sample against this assembly would take a few hours. To avoid this computational burden, let's focus on the first 1 MB of the largest chromosome. Again, seqkit proves its usefulness:

```bash
# Define variables to shorten the command itself
IN_FASTA=./ref/GCF_037325665.1_US_GU_Lsax_2.0_genomic.fna.gz
OUT_FASTA=./ref/chrom1_1Mb.fa

# Some piped seqkit commands
seqkit sort -l -r $IN_FASTA | seqkit head -n 1 | seqkit subseq -r 1:1000000 > $OUT_FASTA
```

You can check the [seqkit docs](https://bioinf.shenwei.me/seqkit/) for the `sort`, `head` and `subseq` commands, but the overall purpose seems clear. Voilà! We've extracted our target 1 Mb. In fact, also thanks to processing with seqkit, the reads we're working with align exactly against this sequence.

!!! tip "How to identify the best reference for your project?" 
    In general, you should aim for your reference assembly to be of the highest possible quality, as defined by N50 and [BUSCO](https://busco.ezlab.org/) completeness, among other statistics. Depending on your organism and your dataset, this might be the best-assembled genome from among your sequenced samples, representing the same or a related species. On the other hand, chromosome-level (or T2T, i.e., telomere-to-telomere) assemblies are available from [public repositories](https://www.ncbi.nlm.nih.gov/datasets/genome/) for many eukaryotes, making them an obvious choice. Assemblies of a very high quality are also available from the [Darwin Tree of Life project](https://portal.darwintreeoflife.org/).

    The choice of reference assembly is far from inconsequential (see, e.g., Mohn et al., 2025), starting at the alignment stage. For example, you might imagine that reads will map better to a con-specific than to a hetero-specific reference genome.
    
## (1.2.2) Alignment

Before we can run the alignment, we need to **index the reference**. Indexing is a one-off procedure that writes a data structure allowing the aligner to navigate the reference quickly. It's as simple as:

```bash
REF=./ref/chrom1_1Mb.fa
bwa-mem2 index $REF
```

This should produce five files with unfamiliar extensions: `.0123`, `.amb`, `.ann`, `.bwt.2bit.64` and `.pac`. The index files should always remain in the same directory as their parent sequence.

Now, we can run the actual alignment using BWA-MEM2. This takes the reference and (trimmed) read files as inputs and produces an alignment in the **SAM format**, which we discuss below.

```bash
# Remember to have SAMPLE defined
SAMPLE="ACF_2"

# BWA-MEM2 inputs:
REF=./ref/chrom1_1Mb.fa
TRIMMED_FASTQ_1=./1.trimmed/${SAMPLE}_R1.fastq.gz
TRIMMED_FASTQ_2=./1.trimmed/${SAMPLE}_R2.fastq.gz

# BWA-MEM2 outputs:
SAM=./2.aligned/${SAMPLE}.sam

# Commands:
mkdir -p ./2.aligned
bwa-mem2 mem \
    -t 1 \
    -R "@RG\tID:${SAMPLE}\tSM:${SAMPLE}\tPL:ILLUMINA\tLB:${SAMPLE}\tPU:${SAMPLE}" \
    $REF \
    $TRIMMED_FASTQ_1 \
    $TRIMMED_FASTQ_2 \
    > $SAM
```
Let's review the flags:

- `-t` specifies the number of threads. This is normally set to be quite large (e.g., 18 or even more), since alignment tends to be relatively slow.
- `-R` specifies a string of characters defining the so-called **read group**. The string starts with `@RG`, with subsequent fields separated by tabs (`\t`). Here, we repeat the sample ID in most fields (though it should primarily go to `SM`, or 'sample'), except `PL` ('sequencing platform'). A 'minimal' read group is essential for variant calling (to link reads with their samples of origin) and enough for our purposes, but the information could be much richer. For instance, a sample sequenced twice on different flowcells would keep one `SM` value but take two read groups with distinct `ID` ('identifier') and `PU` ('platform unit') values.

Note that the output SAM file is specified through `>` rather than a flag. BWA-MEM2 does have an output flag (`-o`), but writing to standard output is a common pattern. Also note how the reference and FASTQ files are provided without any flags, as positional arguments.

## (1.2.3) The SAM format

The SAM (Sequence Alignment/Map) format defines yet another set of conventions (described in full [here](https://samtools.github.io/hts-specs/SAMv1.pdf)) to store sequence information in a text file. But where a FASTQ record describes a read in isolation, a SAM record describes a read together with the position it was assigned in the reference. The file splits into a header and a 'body'.

Let's inspect the header first. We will use a command from the dedicated [SAMtools](https://www.htslib.org/doc/samtools.html) library:

```bash
SAM=./2.aligned/${SAMPLE}.sam
samtools view -H $SAM
```

It is the `-H` flag that restricts the output to the header. Every header line starts with `@` followed by a two-letter record type. You should find three kinds:

- **`@SQ`** - one line per reference sequence, with its name (`SN`) and length (`LN`). Ours has a single `@SQ` line, since we aligned to one sequence only.
- **`@RG`** - the different fields of the read group we passed to BWA-MEM2.
- **`@PG`** - one line per command that touched the file. Two should be shown: one for BWA-MEM2 and one for `samtools view`. The latter is added 'on the fly' as the header is printed to screen, and is not actually part of the file.

Now - the alignments themselves. In contrast to FASTQ, there's a one-to-one correspondence between SAM records and lines of the file. We can request the first two with `head -2` and pipe them to `less -S` for convenient viewing:

```bash
# Note that samtools view omits the header by default
samtools view $SAM | head -2 | less -S
```

!!! tip "On `less`" 
    In contrast to `cat`, `less` lets you navigate its input rather than letting everything scroll past non-interactively (compare the behaviour by substituting `head -200` into the example above!). The `-S` flag stops long lines from wrapping onto the next line, so each record stays on one row. Use the arrow keys to move (up and down by line, left and right by half a screen width), and press `Q` to quit.

Each line consists of 11 mandatory tab-separated fields, followed by optional ones. The meaning of mandatory fields is fixed by position, and below we highlight some of the key ones (see the [specs](https://samtools.github.io/hts-specs/SAMv1.pdf) for a full breakdown):

- **Field 2 - `FLAG`**. An integer encoding a set of yes/no properties, each a power of two, **summed together**. The individual attributes are encoded by smaller integers (or [bits](https://en.wikipedia.org/wiki/Bit_field)), so any combination of them sums to a unique total. You can use `samtools flags` to decode it. For example, `samtools flags 99` returns `PAIRED,PROPER_PAIR,MREVERSE,READ1`, i.e. bits 1, 2, 32 and 64. In human terms, we learn that the read is paired-end (bit 1) and that both mates are properly aligned (bit 2). See section 1.4 of the [specs](https://samtools.github.io/hts-specs/SAMv1.pdf) for the full list.
- **Fields 3 + 4 - `RNAME` + `POS`**. These constitute the alignment itself, specifying the reference sequence (in a real setting - one out of many chromosomes or assembly contigs) and the position of the leftmost aligned base. `RNAME` must match one of the `@SQ` names from the header.
- **Field 5 - `MAPQ`**. The **mapping quality** - a Phred-scaled measure of confidence that the read belongs here rather than anywhere else. Note that this is a different quantity from the FASTQ QUAL scores, which describe base calls rather than placement - a read can consist of perfectly-called bases and still be impossible to place. We will meet MAPQ again in worksheet 1.4, where the `MQ` annotation we filter on is its per-site average.

Uncompressed SAM files tend to get quite big. Luckily, we can easily compress them into a binary BAM format using SAMtools:

```bash
# Specify the input SAM and output BAM
SAM=./2.aligned/${SAMPLE}.sam
BAM=./2.aligned/${SAMPLE}.bam

samtools view -b $SAM > $BAM
```

Where `-b` specifies the output format as BAM. Note that `samtools view` could be connected with a pipe directly to `bwa-mem2 mem`, avoiding the generation of a SAM intermediate altogether.

Finally, let's see how much space we've saved through compression:

```bash
# -l lists one file per line, with details
# -h prints sizes in human-readable units
ls -lh $SAM $BAM

# We don't need the SAM anymore
rm $SAM
```

The BAM takes up nearly four times less space - well worth it.

!!! tip "SAM compression"
    Different levels of output compression can be specified with `samtools view` (`--output-fmt-option level=INT`, from 1 to 9), but higher compression comes at the cost of longer processing time. With small files, the default level 6 is reasonable. The `CRAM` format compresses even further (9 MB here), but it can only be read if the reference is also provided.

## (1.2.4) Marking duplicates

Additional processing is required to make sure our BAM is fit for variant calling. One artefact that becomes apparent after alignment is **read duplication**, when multiple read pairs map to the same position. Depending on the mechanism, two types of duplicates are distinguished: optical and PCR. **Optical duplicates** arise during imaging, when a single cluster on the flow cell is read as two adjacent ones. **PCR duplicates** arise earlier, during library preparation, when amplification produces several copies of one fragment.

Below, we follow the [recommended procedure](http://www.htslib.org/algorithms/duplicate.html) for duplicate marking. This requires some pre-processing of the BAMs:

```bash
# Define input and output;
# 'tmp' stands for 'temporary'
IN_BAM=./2.aligned/${SAMPLE}.bam
OUT_BAM=./2.aligned/${SAMPLE}.tmp.bam

# A few commands...
samtools collate -@ 1 -O $IN_BAM |\
samtools fixmate -@ 1 -m - - |\
samtools sort -@ 1 -o $OUT_BAM -
```
The three SAMtools commands are piped together, and the `-` function as placeholders for inputs (`fixmate`) and outputs. `@` specifies threads. Now, the commands themselves:

- **`collate`** groups reads of the same name together (read from field 1 of the SAM / BAM), so that both mates of a pair sit side by side in the file. 
- **`fixmate`** writes into each read's record a summary of the other read of its pair. Some  (but not all) of this information is already present in fields 7-9 of the SAM / BAM. The `-m` flag in particular specifies adding a 'mate score' - a sum of the mate's base qualities. 
- **`sort`** sorts the file according to reference coordinates, as expected by downstream tools.

We're now ready to actually mark the duplicates: 

```bash
# We return to the original BAM name
IN_BAM=./2.aligned/${SAMPLE}.tmp.bam
OUT_BAM=./2.aligned/${SAMPLE}.bam

samtools markdup -@ 1 -d 100 $IN_BAM $OUT_BAM
rm $IN_BAM
```

Again, `-@` specifies the threads. `-d 100` is more interesting as it sets the optical duplicate distance - the distance on the flow cell within which two identical reads are called optical rather than PCR duplicates. According to the SAMtools docs, a distance of 100 units is recommended for HiSeq-style platforms (2500 for NovaSeq).

Crucially, duplicates are **marked, not removed**. The information is encoded in the `FLAG` (2nd) field of the SAM / BAM (to be precise - its value is incremented by 1024) and is later read by downstream tools such as variant callers. How many duplicates have been marked? We can count by 'fishing' for the tags added by `samtools markdup` using the `grep` Unix command:

```bash
# Make sure the variable points at the final file
BAM=./2.aligned/${SAMPLE}.bam

# Count all reads 
samtools view -c $BAM

# Count all duplicates
samtools view -c -f 1024 $BAM

# Count optical duplicate tags
samtools view $BAM | grep -c 'dt:Z:SQ' 

# Count PCR duplicate tags
samtools view $BAM | grep -c 'dt:Z:LB'
```

In the ACF_2 sample, it appears that PCR duplicates are way more common!

## (1.2.6) BAM QC

Some final sanity checks before we move on. SAMtools provides several options to collect useful statistics on our alignment. Probably the single most informative report comes from `samtools flagstat` which, as you might have guessed, uses the `FLAG` field of the file:

```bash
BAM=./2.aligned/${SAMPLE}.bam
# The report will go to a new subdirectory
FLAGSTAT=./2.aligned/qc/${SAMPLE}.flagstat

mkdir -p ./2.aligned/qc
samtools flagstat $BAM > $FLAGSTAT
```

We saved the `flagstat` report to disk, as you normally would, but for now let's display it with line numbering for ease of orientation:

```bash
# -n adds line numbers
cat -n $FLAGSTAT
```

Every line is a count of reads carrying a particular combination of `FLAG` bits (ignore the `+ 0` part, as the bit it counts is reportedly never set by Illumina instruments). Some key results:

- **Line 5 - duplicates** is the number of duplicates we've seen earlier.
- **Line 8 - primary mapped** is the proportion of reads that the aligner managed to place on the reference at all. This should be satisfyingly high in our example dataset, given how it was created... Across many samples in a real setting, you could be concerned if some display exceedingly low (or high) mapping rates for no apparent reason.
- **Line 12 - properly paired** is a strict assessment of whether both mates not only map but also do so at an expected distance and orientation relative to each other. It should be lower than the mapping rate above.
- **Lines 15-16 - mate mapped to a different chr** are 0 for a trivial reason: we just used one reference sequence. Normally, an excess of cross-chromosome pairs points at structural variation, misassembly or contamination.

What `flagstat` doesn't tell us is where along the reference the reads landed. A very useful overview is provided by `samtools coverage` with the `-m` flag. This draws an ASCII histogram with position on the x axis and **percentage of bases covered** (in bins) on the y axis:

```bash
samtools coverage -m $BAM
```

Alongside the plot it prints the summary statistics. In general, a rather flat histogram is a good sign, while dips or peaks indicate problems - like repeat regions or assembly gaps.

Finally, the richest information is provided by `samtools stats`, which reports several dozen statistics at once:

```bash
STATS=./2.aligned/qc/${SAMPLE}.stats
samtools stats $BAM > $STATS
```

The report is organised by two-letter section codes in the first column. `SN` holds the summaries; the remaining sections are whole distributions rather than single values. `IS` are insert sizes, `RL` read lengths, `COV` coverage, `GCF`/`GCL` GC content, and so on - each a table you could plot directly.

Let's at least inspect the `SN` lines. We can pull them out using `grep`, a Unix utility for searching lines that match a [regular expression](https://en.wikipedia.org/wiki/Regular_expression). We ask for lines that start (`^`) with `SN`:

```bash
grep "^SN" $STATS
```

Some important additional information include:

- **`reads MQ0`** shows the number of aligned reads with a mapping quality of 0. These are simply counted as mapped by `flagstat`.
- **`error rate`** - is the proportion of aligned bases that differ from the reference. 
- **`insert size average`** is the average length of inserts as calculated from the alignment, while **`insert size standard deviation`** is.. the standard deviation. The latter number reveals the frequency at which the mates map at implausible distances from each other. 

!!! tip "Collecting BAM stats"
    In a 'production pipeline', we would probably like to check our BAMs in bulk rather than examining one sample at a time. The [MultiQC](https://multiqc.info/) software has been designed to help with exactly this task on FASTQ and BAM files, taking FastQC, fastp and SAMtools reports as input.

## (1.2.7) Process all samples

Just like previously, there remain 10 samples that need to be processed in an analogous manner. Using the commands introduced above and techniques from the previous worksheet, try and write a shell script to process the remaining samples. For simplicitly, focus on the command that are essential to producing the final BAM.

??? success "Show the answer"
    ```bash
    #!/bin/bash
    set -euo pipefail

    # Run as: ./run_align.sh samples.txt

    # Samples are read from a file, one name per line.
    IN_FILE=$1
    readarray -t SAMPLES < "$IN_FILE"

    # The reference is the same for every sample.
    REF=./ref/chrom1_1Mb.fa

    mkdir -p ./2.aligned ./2.aligned/qc

    for SAMPLE in ${SAMPLES[@]}; do
        echo "Processing sample ${SAMPLE}..."

        TRIMMED_FASTQ_1=./1.trimmed/${SAMPLE}_R1.fastq.gz
        TRIMMED_FASTQ_2=./1.trimmed/${SAMPLE}_R2.fastq.gz
        SAM=./2.aligned/${SAMPLE}.sam
        BAM=./2.aligned/${SAMPLE}.bam
        TMP_BAM=./2.aligned/${SAMPLE}.tmp.bam
        FLAGSTAT=./2.aligned/qc/${SAMPLE}.flagstat

        bwa-mem2 mem \
            -t 1 \
            -R "@RG\tID:${SAMPLE}\tSM:${SAMPLE}\tPL:ILLUMINA\tLB:${SAMPLE}\tPU:${SAMPLE}" \
            $REF \
            $TRIMMED_FASTQ_1 \
            $TRIMMED_FASTQ_2 \
            > $SAM

        samtools view -b -o $BAM $SAM
        rm $SAM

        samtools collate -@ 1 -O $BAM |\
        samtools fixmate -@ 1 -m - - |\
        samtools sort -@ 1 -o $TMP_BAM -

        samtools markdup -@ 1 -d 100 $TMP_BAM $BAM
        rm $TMP_BAM

        samtools flagstat $BAM > $FLAGSTAT

        echo "Finished sample ${SAMPLE}."
    done
    ```
