    1.1. Read QC & trimming¶

    Learning objectives

    By the end of this worksheet, you will:

    • Understand FASTQ file format and how it relates to the sequencing procedure.
    • Perform read quality control and trimming.
    • Become more acquainted with the Unix command line.
    • Process multiple samples with loops and package your work in a shell script.

    (1.1.1) Sequencing-by-synthesis recap¶

    Sequencing by synthesis (SBS) is the core of Illumina technology. While the chemical details do not matter for our purposes, a conceptual understanding helps interpret the files passed over from a sequencing facility. The main stages of a paired-end SBS procedure can be summarised as follows:

    1. Library prep - the DNA is sheared into fragments of target length, typically a few hundred base pairs. Different adapter sequences are then ligated to the two ends of each fragment (now called an 'insert'). Each adapter contains a flow-cell binding site and a sequencing primer.
    2. Cluster generation / bridge amplification - The flow cell is a glass slide with lanes. DNA molecules bind to oligonucleotides (or 'oligos') tethered to the lane, bend over to bind a neighbouring oligo, and are copied. Repeated, this turns every molecule into a cluster of hundreds of identical copies.
    3. Sequencing - Starting from the first type of sequencing primer, fluorescent nucleotides are incorporated one per cycle. Every cycle, the flow cell is imaged, and the colour of each cluster is read off. After a given number of cycles (say, 150), the forward reads are complete. The templates are then flipped over, and the whole procedure is repeated from the 2nd sequencing primer to obtain reverse reads.

    Together, these 3 videos from Illumina will hopefully make it quite clear: video 1, video 2, video 3 (watch later).

    (1.1.2) Orientation¶

    Having connected to the remote machine, let's locate ourselves - where are we? You should start today's work in your home directory, so let's verify you're in the right place:

    # This should print /home/userX, where X is your user ID
pwd # stands for 'print working directory'

# If you're not there:
cd ~ # equivalent to cd /home/userX, where X is your user ID

# Double-check your home directory
echo $HOME

    Note that, by default, the HOME environment variable stores the path to your home directory. Inside it, we can create a directory (=folder) for today's project...

    mkdir ./reads2snps

    ...and move inside it!

    cd ./reads2snps

    From now on, most commands of the Reads-to-SNPs module will assume that we are inside the ${HOME}/reads2snps directory. This means that, rather than the full path (e.g., /home/user1/reads2snps/your-directory), the commands will invoke relative paths (e.g., ./your-directory).

    (1.1.3) Back from the sequencing facility¶

    Let's start by viewing the contents of /home/Share/reads2snps/original_files, a directory that stores the data we're going to work with in this module:

    ls /home/Share/reads2snps/original_files

    You should see multiple sub-directories with slightly cryptic names. These names are actually sample codes, and each subdirectory holds the sequencing data for an individual Littorina snail. We can peek inside one:

    ls /home/Share/reads2snps/original_files/ACF_2

    Inside, you should see multiple compressed FASTQ (.fastq.gz) files with compound names. This is typical for raw read data returned from a sequencing facility - in fact, the contents of the subdirectory looks almost exactly like what Sean received back in 20XX.

    On original_files

    Note that additional metadata files might be also given. Also note that, for the purpose of the tutorial, we have prepared subsampled versions of the original files that can be processed in seconds-to-minutes rather than hours.

    For convenience, let's immediately copy over everything to your private original_files directory:

    # Create private original_files
mkdir ./original_files

# Copy a directory and all its subdirectories (-r)
cp -r /home/Share/reads2snps/original_files/* ./original_files

    Where the -r flag stands for 'recursive' and ensures that all the subdirectories are copied over. It is always good practice to carry on some basic checks on the integrity of a dataset. First, there should be 11 sample directories. Second, each should hold a variable, but always even, number of files. Variable - because reads sequenced on distinct lanes are packaged into separate files. Even - because each lane delivers a package of forward and reverse reads, as denoted with the _1 and _2 suffixes (look just before the format extension).

    # Count subdirectories
ls ./original_files | wc -l

# Count _1 and _2 files in a few sample directories
ls ./original_files/ACF_2/*_1.fastq.gz | wc -l
ls ./original_files/ACF_2/*_2.fastq.gz | wc -l

    The so-called pipe | passes the output fo the ls command to wc -l that counts the number of files. Also of note - the * symbol is a wildcard that matches all files ending in a given suffix + extension. If everything looks about right, we're ready start building our pipeline!

    (1.1.4) The FASTQ format¶

    So, what kind of format is FASTQ? Developed roughly a decade after the more familiar FASTA, FASTQ was initally an ad hoc solution to the problem of keeping a sequence and its companion per-base quality values in sync. Over time, it's become the standard (see Cock et al., 2010, for an interesting historical overview).

    Let's inspect one of the FASTQ files we've just copied over. We will define the sample name in an environment variable SAMPLE. This is often useful if we want to substitute the same string of characters (such as sample name) into different paths.

    SAMPLE="ACF_2"

# Check the value of SAMPLE
echo $SAMPLE

# See how SAMPLE can be substituted into a path
# {} is used for clarity but is not essential
echo "./original_files/${SAMPLE}/190109_E00306_0399_AHVLYNCCXY_4_11533BR0010L01_1.fastq.gz"

    The value saved in SAMPLE will persist as long as your terminal window is open, but will need to be redefined upon a reboot. Then, we can use zcat - a compression-aware variant of the standard cat Unix command for concatenating (here - just displaying) the contents of a file - piped with head, to only display the first 8 lines. 

    zcat ./original_files/${SAMPLE}/190109_E00306_0399_AHVLYNCCXY_4_11533BR0010L01_1.fastq.gz | head -8

    You might notice that a pattern repeats every 4 lines. This is because, in contrast to FASTA, each FASTQ sequence entry consist of 4, rather than 2, lines. These are, respectively:

    • The header that starts with a '@'. The header can have arbitrary length and store arbitrary information. Here, it consists of two main 'chunks' separated by a space. The first chunk complements the file name (specifying the instrument, flowcell, etc.), with the last two integers being the coordinates of the read's origin within the lane. These coordinates are what connects forward and reverse reads between the _1 and _2 files.
    • The sequence of bases, where 'N' stands for a base that the instrument could not call. Note that, just like in FASTA, the sequence line can be 'wrapped', i.e. split across multiple lines.
    • A '+' character or optionally a repeat of the header.
    • Phred-scaled QUAL (quality) scores. QUAL values are calculated from per-base error probabilities \(P_e\) (themselves derived from SBS colour intensities) and following the formula \(Q = -10 \log_{10} P_e\). In other words, \(Q = 0\) corresponds to a base that's definitely wrong, \(Q = 10\) corresponds to \(P_e = 0.1\), \(Q = 20\) corresponds to \(P_e = 0.01\) (1% chance of error), etc. Each QUAL value sits directly below the base it scores, so the sequence and quality lines are always the same length (and can be similarly wrapped). The scores are encoded using ASCII printable characters.

    The QUAL line

    Only ASCII characters from 33 onwards are used to encode QUAL scores. Note that @ and + are used to both encode QUAL scores and to demark the 1st (header) and 3rd lines, respectively. While the ASCII solution already provides a file-size advantage, modern Illumina technologies apply score-binning strategies. For example, NovaSeq 6000 uses scores of 12, 23 and 37 (-, 8 and F), plus a null score (#, or 2) for no-calls.

    Another QUAL-related issue to keep in mind is the 'lossy' compression of FASTQ files downloaded from public repositories. For example, files deposited on SRA (Sequence Read Archive) - or on its ENA (European Nucleotide Archive) mirror - may be served in the SRA Lite format, which effectively erases QUAL scores. If QUAL scores matter for your analysis (as they often do), explore solutions for downloading the original, unspoiled FASTQs.

    There's one more task remaining before we feed our FASTQs to bioinfomatic software, and it allows us to emphasise an important point. FASTQ files are essentially text files. The task is to combine all the _1 and _2 files into total reverse and forward read files, respectively. The solution is standard for text files - use concatenation.

    As prep, let's create a directory to store the concatenated files:

    mkdir ./0.raw

    Note that the directory name starts with 0, which is just an index to keep track of subsequent processing steps. In larger pipelines, this convention is particularly useful.

    Then, we can perform concatentaion of all _1, and separately, all _2 files using the cat command and the handy * wildcard: 

    cat ./original_files/${SAMPLE}/*_1.fastq.gz > ./0.raw/${SAMPLE}_R1.fastq.gz
cat ./original_files/${SAMPLE}/*_2.fastq.gz > ./0.raw/${SAMPLE}_R2.fastq.gz

    This does the job for one sample. However, you might imagine that copying-pasting the commands while redefining the SAMPLE variable each time could take some effort. Luckily, a handy pattern exists in bash (and many other languages) - a for loop.

    To 'loop over' the different samples, we've prepared a newline-separated file with all the sample names. Copy it from the /home/Share/reads2snps directory:

    cp /home/Share/reads2snps/samples.txt ./samples.txt

    And read its contents as a bash array using the readarray command. In bash, you can think of an array as a space-separated list.

    readarray -t SAMPLES < ./samples.txt

# View the array
# Here, {} is required
echo ${SAMPLES[@]}

    Notice how viewing the array requires additional 'unpacking' of individual values using [@]. Finally, we can loop over the sample names, performing our desired concatenation:

    for SAMPLE in ${SAMPLES[@]}; do
    cat ./original_files/${SAMPLE}/*_1.fastq.gz > ./0.raw/${SAMPLE}_R1.fastq.gz
    cat ./original_files/${SAMPLE}/*_2.fastq.gz > ./0.raw/${SAMPLE}_R2.fastq.gz
    echo "Finished sample ${SAMPLE}."
done

    Note the characteristic for-loop keywords: for, do and done. While the indentation of contents (here, the two cat + echo line) is not mandatory in bash loops, it does look more legible (and pretty) this way.

    In general, with a little Unix magic, we can do pretty much anything with FASTQ files. This includes relatively simple stuff, like counting the number of reads in a file:

    echo $(( $(zcat ./0.raw/${SAMPLE}_R1.fastq.gz | wc -l) / 4 ))

    Or more complex stuff, like computing the average read length (you can learn more about awk here):

    zcat ./0.raw/${SAMPLE}_R1.fastq.gz | awk 'NR%4==2 {sum+=length($0); n++} END {print sum/n}'

    On the other hand, specialised suites of software exist to do exactly these operation for us. Here, we get some useful info on all our FASTQ files at once using seqkit. To use this you will need to make sure you have activated the conda environment for the course.

    seqkit stats ./0.raw/*.fastq.gz

    The table produced by seqkit is a good diagnostic of all the files being uncorrupted - problems such as files truncation would be indicated by diffent numbers of reads in reverse / forward files (or a failure of the seqkit command).

    (1.1.5) Quality control¶

    While important, QUAL scores are not the only source of information regarding sequence quality, with other useful clues implicit to the sequences themselves. All these source of info can be jointly assessed using reports produced by the FastQC program. Let's first run it on an example sample.

    # Remember to have SAMPLE defined
SAMPLE="ACF_2"

# FastQC inputs:
RAW_FASTQ_1=./0.raw/${SAMPLE}_R1.fastq.gz
RAW_FASTQ_2=./0.raw/${SAMPLE}_R2.fastq.gz

# Commands:
mkdir -p ./0.raw/qc
fastqc -t 1 \
    --outdir ./0.raw/qc \
    $RAW_FASTQ_1 $RAW_FASTQ_2

    Note how the arguments to fastqc are split between multiple lines using backslash (\) characters - for clarity, we will often use this way of formatting longer commands. --outdir defined the output directory to write FastQC reports; the -t flag specifies the number of threads, i.e., the number of concurrent computations. In FastQC, threads translate, more simply, to the number of input files that are processed in parallel.

    Multi-threading

    Most bioinformatic programs can split their work across multiple threads, cutting runtime roughly in proportion to the number you give them. We stick to -t 1 throughout, since our files are small. On a real dataset, you would use as many threads as your machine provides.

    After FastQC finished processing both inputs, check ./0.raw/qc with ls - you should be able to find two HTML reports. Using a command (e.g., scp -i cX.pem userX@ip-address:/home/userX/read2snps/0.raw/qc/*.html . run from your local machine), Filezilla or another method, download the reports to your local machine. Both reports should look very encouraging, indicating no issues with the read data. For a contrast, you can see an example of a bad FastQC report here.

    (1.1.5) Adapter trimming & filtering¶

    Even with high-quality read data, there are still good reasons to trim our reads. Individual reads might display various artefacts: very short inserts (in low-input libraries, adapters can even ligate to each other, producing insert-free adapter dimers) or a steeper-than-average drop-off in base quality, to name a few. For the trimming task, we will use fastp - Trimmomatic is one popular alternative.

    Again, let's use the example sample to demonstrate running fastp:

    # Remember to have SAMPLE defined
SAMPLE="ACF_2"

# fastp inputs:
RAW_FASTQ_1=./0.raw/${SAMPLE}_R1.fastq.gz
RAW_FASTQ_2=./0.raw/${SAMPLE}_R2.fastq.gz

# fastp outputs:
TRIMMED_FASTQ_1=./1.trimmed/${SAMPLE}_R1.fastq.gz
TRIMMED_FASTQ_2=./1.trimmed/${SAMPLE}_R2.fastq.gz
FASTP_HTML=./1.trimmed/qc/${SAMPLE}_fastp.html

# Commands:
mkdir -p ./1.trimmed ./1.trimmed/qc
fastp \
    -i $RAW_FASTQ_1 -I $RAW_FASTQ_2 \
    -o $TRIMMED_FASTQ_1 -O $TRIMMED_FASTQ_2 \
    --thread 1 \
    -u 40 -q 15 \
    -g -c -y -Y 30 \
    --html $FASTP_HTML \
    --report_title $SAMPLE

    A few more flags here, so let's break them down:

    • -u 40 allows up to 40% of a read's bases to be 'unqualified' (see below) - above that, the whole read, and its mate, are discarded rather than trimmed. (This is on by default.)
    • -q 15 sets the QUAL score below which a base counts as 'unqualified'.
    • -g enables the trimming of poly-G tails introduced by some modern Illumina technologies (such as NextSeq or NovaSeq - not relevant here, but good to remember).
    • -c enables base correction in regions where forward and reverse reads overlap.
    • -y enables a complexity filter, with -Y 30 setting its threshold - reads with <30% base-to-base change are dropped (think of a repetitive region such as AAAAA...)
    • --html and --report_title define a fastp report that compares the properties of reads before and after trimming - take a look, if interested!

    Note that fastp detects and trims a range of standard Illumina adapters by default. As a basic sanity check, it makes sense to compare the length of reads before and after trimming using seqkit stats:

    seqkit stats ./0.raw/${SAMPLE}*.fastq.gz
seqkit stats ./1.trimmed/${SAMPLE}*.fastq.gz

    (1.1.6) A shell script¶

    Up to now, we've been executing commands directly from the command line. That works, but once you close your terminal, the record of what you've run is gone. A shell script is simply those same commands saved in a file, so the whole analysis can be rerun in one go — and the file itself becomes a permanent record of what you did.

    We now have everything we need: FastQC and fastp commands that work on one sample, and an understanding of how a for loop can be used to iterate over all samples. Let's put everything together. We suggest that you initially open a new local file and call it run_qc_trim.sh, where the .sh extension identifies a shell script.

    The first line of a script is the shebang, which defines bash as the interpreter for our script:

    #!/bin/bash

    By default, bash carries on after an error, so a script can fail at step 1 and keep running. The next line prevents this behaviour (by terminating the run upon any error) and will save you lots of debugging in the future:

    set -euo pipefail

    Our script needs to know which samples to process. Rather than hard-coding the file name, we read it from the first argument given on the command line. This is available as $1:

    IN_FILE=$1
readarray -t SAMPLES < "$IN_FILE"

    Now, to make our script self-sufficient, we want it to create all its output directories. mkdir normally throws an error if the requested directory exists, but this is prevented by the -p flag:

    mkdir -p ./0.raw ./1.trimmed ./0.raw/qc ./1.trimmed/qc

    Then the loop itself. To avoid rewriting the FastQC and fastp commands, let's make it define all inputs / outputs as variables...

    # Start of loop
for SAMPLE in ${SAMPLES[@]}; do
    echo "Processing sample ${SAMPLE}..."

    RAW_FASTQ_1=./0.raw/${SAMPLE}_R1.fastq.gz
    RAW_FASTQ_2=./0.raw/${SAMPLE}_R2.fastq.gz
    TRIMMED_FASTQ_1=./1.trimmed/${SAMPLE}_R1.fastq.gz
    TRIMMED_FASTQ_2=./1.trimmed/${SAMPLE}_R2.fastq.gz
    FASTP_HTML=./1.trimmed/qc/${SAMPLE}_fastp.html

    ...and finally the two commands, copied straight from the previous sections:

        fastqc -t 1 \
        --outdir ./0.raw/qc \
        $RAW_FASTQ_1 $RAW_FASTQ_2

    fastp \
        -i $RAW_FASTQ_1 -I $RAW_FASTQ_2 \
        -o $TRIMMED_FASTQ_1 -O $TRIMMED_FASTQ_2 \
        --thread 1 \
        -u 40 -q 15 \
        -g -c -y -Y 30 \
        --html $FASTP_HTML \
        --report_title $SAMPLE

    echo "Finished sample ${SAMPLE}."
done
# End of loop

    Your script is ready! You should now transfer it to your reads2snps directory. One last step: a text file is not executable by default, so we need to grant it permission to run:

    chmod +x run_qc_trim.sh

    And run it, passing the sample list as the argument:

    ./run_qc_trim.sh samples.txt

    You can find the whole script in the box below.

    The complete script 
    #!/bin/bash
set -euo pipefail

# Run as: ./run_qc_trim.sh samples.txt

# Samples are read from a file, one name per line.
IN_FILE=$1
readarray -t SAMPLES < "$IN_FILE"

mkdir -p ./0.raw ./1.trimmed ./0.raw/qc ./1.trimmed/qc

for SAMPLE in ${SAMPLES[@]}; do
    echo "Processing sample ${SAMPLE}..."

    RAW_FASTQ_1=./0.raw/${SAMPLE}_R1.fastq.gz
    RAW_FASTQ_2=./0.raw/${SAMPLE}_R2.fastq.gz
    TRIMMED_FASTQ_1=./1.trimmed/${SAMPLE}_R1.fastq.gz
    TRIMMED_FASTQ_2=./1.trimmed/${SAMPLE}_R2.fastq.gz
    FASTP_HTML=./1.trimmed/qc/${SAMPLE}_fastp.html

    fastqc -t 1 \
        --outdir ./0.raw/qc \
        $RAW_FASTQ_1 $RAW_FASTQ_2

    fastp \
        -i $RAW_FASTQ_1 -I $RAW_FASTQ_2 \
        -o $TRIMMED_FASTQ_1 -O $TRIMMED_FASTQ_2 \
        --thread 1 \
        -u 40 -q 15 \
        -g -c -y -Y 30 \
        --html $FASTP_HTML \
        --report_title $SAMPLE

    echo "Finished sample ${SAMPLE}."
done
